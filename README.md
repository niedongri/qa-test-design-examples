# 需求上限从5改成3，测试用例应该怎样跟着改？

维护一份用例时，一个常见变化是：允许的数量范围从1—5改成1—3。直接全局替换数字，很容易改变不该改变的预期，或者漏掉新的边界。

这篇文章用虚构的库存预留需求，演示如何保留用例编号、修改边界断言，并把未定义的规则继续留作待确认。文末附关联的WorkBuddy付费技能入口，由本项目维护者发布；正文可以独立阅读和复现。

**示例说明：**以下需求和用例均为人工构造的合成资料。设计JSON已通过本地工具的结构与追溯映射检查；这些用例未执行，本文也不是WorkBuddy本次模型生成的运行记录。规则计算示例只说明预期如何变化，不连接真实业务系统。

## 先把变化说清楚

旧版规则：已认证客户可以对自己有权限的商品提交整数数量q，1≤q≤5。成功后库存减q，新增一条预留记录。非法数量应拒绝，且不改变库存和记录。

本次只把上限5改成3，其他规则保持：

- 客户A不能预留仅属于客户B的商品。
- 只剩1件库存时，两个不同请求同时各预留1件，必须且仅有一个成功。
- 幂等键有效期、重复请求返回规则和响应延迟要求没有定义，继续作为待确认问题。

先圈定“只改数量上限”，后面就有依据判断权限与并发用例是否应该保留。

## 不同数值受到的影响不同

| 数量q | 旧版数量规则 | 新版数量规则 | 用例维护动作 |
|---|---|---|---|
| 0 | 拒绝 | 拒绝 | 保留原下界外用例和无副作用断言 |
| 1 | 接受 | 接受 | 保留下边界用例 |
| 2 | 接受 | 接受 | 保留现有合法值用例 |
| 3 | 接受，但旧示例未单列此值 | 接受，且成为新上边界 | 补一条显式新边界用例 |
| 4 | 接受 | 拒绝，且成为新上界外邻值 | 修改原用例预期，不重编编号 |
| 5 | 接受 | 拒绝 | 修改原用例预期，不重编编号 |
| 6 | 拒绝 | 拒绝，但不再紧邻上界 | 保留为普通超限检查，按风险重新评估优先级 |
| 1.5 | 拒绝 | 拒绝 | 保留整数约束检查 |

这些“接受”仅指满足数量约束；业务最终能否接受，还要同时满足认证、权限和库存等前置条件。

## 用例编号保留，断言与依据一起改

在这份合成设计中：

| 用例编号 | 旧标题/作用 | 新标题/作用 | 处理方式 |
|---|---|---|---|
| TC-D2-STOCK-003 | 预留合法数量4 | 拒绝超出新上界的数量4且不扣库存 | 保留编号，修改标题、预期和映射依据 |
| TC-D2-STOCK-004 | 预留合法数量5 | 拒绝超出新上界的数量5且不扣库存 | 保留编号，修改预期和映射依据 |
| TC-D2-STOCK-006 | 拒绝无效数量6 | 拒绝无效数量6 | 保留编号；本示例从P1调整到P2，这不是所有项目的固定评级 |
| TC-D2-STOCK-010 | 旧设计没有这一条 | 接受新上边界3并核对扣减 | 新增编号，保留新增理由 |

以TC-D2-STOCK-003为例，新版设计应该同时写清楚：

1. 前置条件：客户A已认证，对商品S有权限；S库存10，预留记录0。
2. 操作：A对S提交q=4的预留请求，再查询库存和预留记录。
3. 预期：业务拒绝；库存仍为10，预留记录仍为0。
4. 变更依据：数量上限由5变成3，4不再是合法值。

“请求被拒绝”与“数据没有变化”都要写，不能只把成功提示改成失败提示。资料没有规定具体接口URL和错误码时，不要把猜测写成已经确认的验收标准。

## 一个可以运行的规则计算例子

下面的Python代码仅演示数量约束，不是对真实API或WorkBuddy的测试。无需第三方依赖。

```python
def quantity_expectation(q, upper):
    valid = type(q) is int and 1 <= q <= upper
    return "接受" if valid else "拒绝"


if __name__ == "__main__":
    print("q\t上限5\t上限3")
    for q in (0, 1, 2, 3, 4, 5, 6, 1.5):
        print(q, quantity_expectation(q, 5),
              quantity_expectation(q, 3), sep="\t")
```

4和5的结果会从接受变成拒绝；3的结果虽然没变，但它的边界角色变了。这就是只比较预期结果还不够的原因。

可直接保存上述代码，或运行同目录的[示例脚本](boundary_change_demo.py)：`python -X utf8 boundary_change_demo.py`。

## 不随本次变更消失的问题

权限、并发以及拒绝后的数据不变性，需要继续在设计中保留。幂等和延迟规则仍然没有定义，应列在缺口与待确认清单中；不能因为表格变长，就宣称所有风险都已覆盖。

这份示例的旧设计有9条可执行设计用例，新设计有10条。这里的“可执行”指步骤和断言具备设计依据，执行状态仍是未执行。结构和映射检查通过，也不代表业务测试已经通过或语义覆盖完整。

实际维护时，建议一起保留：原始需求及版本、用例与稳定编号、需求/条件追溯、变更理由、待确认问题以及原始设计文件。CSV便于表格使用，原始设计文件便于继续修订。
